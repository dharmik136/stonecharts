# What "Visual Integrity" Means for Regulated Reporting

A chart in a quarterly filing looks different from last quarter's version of the
same chart. Was the data different? Was the rendering library updated? Did a
dependency change the output? Did someone edit the SVG by hand?

In most organizations, the answer is: "We don't know, but it looks close enough."

In regulated environments — insurance reporting, actuarial exhibits, financial
risk disclosures, clinical trial visualizations — "close enough" is expensive.
The investigation is manual, the documentation is ad hoc, and the cost is
hidden in review cycles nobody tracks.

## Three layers of the problem

### 1. Rendering is not reproducible

Most chart systems do not guarantee the same input produces the same output.
A library update, a dependency patch, a platform difference, or re-running the
same code can produce visually similar but byte-different SVG. Two of five major
systems we tested embed random identifiers on every render.

When the output is not reproducible, "what changed?" requires a human visually
comparing two charts. At scale — hundreds of charts per quarterly cycle — that
comparison is not done. Changes slip through.

### 2. There is no evidence trail

Even when a chart changes intentionally — new data, a correction — there is no
structured record of what changed and why. The chart is regenerated, the new
version replaces the old one, and the only evidence is a git diff of a large
SVG blob no reviewer will read line by line.

Code changes have commit messages, reviews, and CI pipelines. Charts are treated
as disposable output, not governed artifacts.

### 3. Cross-system drift is invisible

When charts are generated by more than one system — a Python analysis pipeline
and a Go production service, or two teams using different tools — drift between
them is invisible until a client or auditor notices it. There is no automated
check that says "these two systems are producing the same chart for the same
data."

## What visual integrity would look like

1. **One specification.** A single, language-neutral chart definition consumed
   by every system that renders charts. Not "similar configurations in two
   libraries" — the same file, the same schema, the same semantics.

2. **Deterministic rendering.** Same spec, same bytes. Every time. Regardless
   of language, machine, or invocation count. No random IDs, no
   platform-dependent drift, no implicit state.

3. **Conformance evidence.** Every CI run produces a verifiable record: input
   spec, output SVG, SHA-256 hash, comparison result. When something changes,
   the evidence classifies whether the spec changed (intentional) or the
   renderer changed (unintentional).

4. **Policy enforcement.** Approved chart types, color palettes, accessibility
   requirements, and format constraints enforced by the system, not by review
   checklists.

## Who needs this — and who does not

Not everyone. If you build interactive dashboards for internal use, visual
integrity is over-engineering. The audience is internal, the charts are
ephemeral, and "it looks right" is sufficient.

Visual integrity matters when:

- Charts appear in **external-facing documents** that are filed, audited, or
  contractually binding
- **Multiple systems** produce charts from the same data, and consistency is an
  implicit expectation
- A **dependency upgrade** could change output without anyone noticing until a
  client complains
- The cost of a **visual discrepancy** is not "someone opens a ticket" but
  "someone explains it to a regulator"
