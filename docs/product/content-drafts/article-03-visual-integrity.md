# What "Visual Integrity" Means for Regulated Reporting

When a quarterly filing contains a chart that looks different from the previous
quarter's version of the same chart, someone has to explain why. Was the data
different? Was the rendering library updated? Did a dependency change the output?
Did someone edit the SVG by hand?

In most organizations, the answer is: "We don't know, but it looks close enough."

In regulated environments — insurance reporting, actuarial exhibits, financial risk
disclosures, clinical trial visualizations — "close enough" is expensive. The
investigation is manual, the documentation is ad hoc, and the cost is hidden in
review cycles that nobody tracks.

## The problem has three layers

### 1. Rendering is not reproducible

Most chart rendering systems do not guarantee that the same input produces the same
output. A library update, a dependency patch, a platform difference, or even
re-running the same code can produce visually similar but byte-different SVG. Two of
five major systems we tested embed random identifiers in their output on every
render.

When the output is not reproducible, you cannot answer "what changed?" without a
human visually comparing two charts side by side. At scale — hundreds of charts per
quarterly cycle — that comparison is not done. Changes slip through.

### 2. There is no evidence trail

Even when a chart does change intentionally — new data, new formatting, a correction
— there is no structured record of what changed and why. The chart is regenerated,
the new version replaces the old one, and the only evidence is a git diff of a
binary or a large SVG blob that no reviewer will read line by line.

Contrast this with code, where every change has a commit message, a review, and a
CI pipeline that runs tests. Charts are treated as disposable output, not as
governed artifacts.

### 3. Cross-system drift is invisible

In organizations where charts are generated by more than one system — a Python
analysis pipeline and a Go production service, or a data team and a platform team
using different tools — drift between the systems is invisible until a client or
auditor notices it. There is no automated check that says "these two systems are
producing the same chart for the same data."

## What would "visual integrity" look like?

A visual integrity approach would mean:

1. **One specification.** A single, language-neutral chart definition that both the
   analysis pipeline and the production service consume. Not "similar
   configurations in two different libraries" — the same file, the same schema, the
   same semantics.

2. **Deterministic rendering.** The same specification produces the same output,
   byte for byte, regardless of which language runs the renderer, which machine it
   runs on, or how many times it runs. No random IDs, no platform-dependent
   floating-point drift, no implicit state.

3. **Conformance evidence.** Every release, every deployment, every CI run produces
   a verifiable record: the input specification, the output SVG, a SHA-256 hash,
   and a comparison result. When something changes, the evidence shows exactly what
   changed and classifies whether the input spec changed (intentional) or the
   renderer changed (unintentional).

4. **Policy enforcement.** Approved chart types, color palettes, accessibility
   requirements, and format constraints are enforced by the system, not by review
   checklists. A chart that violates the policy fails validation before it reaches
   the report.

## Who needs this?

Not everyone. If you build interactive dashboards for internal use, visual integrity
is over-engineering. The audience is internal, the charts are ephemeral, and "it
looks right" is a sufficient standard.

Visual integrity matters when:

- The charts appear in **external-facing documents** that are filed, audited, or
  contractually binding
- **Multiple teams or systems** produce charts from the same data, and consistency
  between them is an implicit expectation
- A **dependency upgrade** or **platform migration** could change chart output
  without anyone noticing until a client complains
- The cost of a **visual discrepancy** is not "someone opens a ticket" but "someone
  explains it to a regulator"
